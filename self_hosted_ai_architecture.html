In-House AI Cluster Architecture (Mac Mini Cluster)

This guide outlines how to leverage your 4-5 Mac Minis to build a private, high-performance, in-house AI platform for 100+ users. By self-hosting LLMs, you will reduce external API token usage to zero for standard tasks, keep your company data secure, and provide a unified chat interface.

1. High-Level Architecture Diagram

Here is how your in-house AI cluster will function. A central load-balancer and gateway (LiteLLM) will distribute incoming requests from your users across the 4-5 Mac Minis running Ollama.

2. Core Technology Stack

To build this setup, we recommend the following open-source, production-ready stack:

Component Technology Why We Use It
User Frontend Open WebUI Sleek, ChatGPT-like interface. Supports user authentication, custom system prompts, Retrieval-Augmented Generation (RAG) for documents, and playground modes.
Gateway & Load Balancer LiteLLM Proxy Acts as a single OpenAI-compatible API gateway. Distributes loads across your Ollama workers, handles API keys/budgets for internal developers, and supports fallback to commercial APIs (e.g., Gemini, OpenAI) if local resources are saturated.
Inference Engine Ollama Easiest way to run LLMs on macOS. Uses Apple Silicon Metal acceleration automatically, handles model downloads, and provides a clean local API.
Containerization Docker / Docker Compose Simplifies deploying the central control services (LiteLLM, Open WebUI, Database) on your primary Mac Mini.

3. Hardware Capability & Model Selection

Apple Silicon Mac Minis utilize Unified Memory (RAM), which is shared between the CPU and GPU. This is excellent for LLMs, as local inference speed is almost entirely limited by memory bandwidth.

Depending on the RAM configurations of your Mac Minis, here are the models you can run efficiently:

Mac Mini RAM Recommended Quantized Models Speed / Performance Profile
16 GB RAM Qwen 2.5 (7B), Llama 3.1 (8B), Mistral (7B) Fast (~30-50 tokens/sec). Great for general summaries, brainstorming, and basic coding tasks.
24 GB RAM Qwen 2.5 (14B), Gemma 2 (9B), Llama 3.1 (8B) Balanced. Strong reasoning capabilities, fits comfortably with high context length.
64 GB+ RAM Qwen 2.5 (32B), Command-R (35B), Llama 3.1 (70B Q4) High reasoning, slower generation (~10-15 tokens/sec). Best for complex code generation, logical reasoning, and data synthesis.
💡 Scaling to 100+ Users:

Since you have 4-5 Mac Minis, you can load-balance the same model (e.g., qwen2.5:7b or llama3.1:8b) across all of them. This allows the cluster to handle 10 to 15 concurrent users actively streaming responses at the same time without significant queueing.

4. Configuration Templates

A. Worker Nodes (Ollama Configuration)

On each of your Mac Minis, install Ollama. By default, Ollama only listens on localhost. To allow your LiteLLM Gateway to reach them:

  1. Open your terminal on each Mac Mini and run: 
    # Set environment variable to bind to all network interfaces
launchctl setenv OLLAMA_HOST "0.0.0.0"
  2. Restart the Ollama application.
  3. Download your chosen models on each Mac Mini (e.g., ollama pull qwen2.5:7b).

B. Controller Node (LiteLLM & Open WebUI)

Choose one Mac Mini (or a separate server) to act as the Gateway. Create a directory (e.g., ~/ai-gateway) and place the following two configuration files there.

1. config.yaml (LiteLLM Configuration)

This config file sets up load balancing across your worker Macs. Replace the IP addresses (192.168.1.X) with the actual local IP addresses of your Mac Minis.

model_list:
  - model_name: internal-llm
    litellm_params:
      model: ollama/qwen2.5:7b
      api_base: http://192.168.1.101:11434
  - model_name: internal-llm
    litellm_params:
      model: ollama/qwen2.5:7b
      api_base: http://192.168.1.102:11434
  - model_name: internal-llm
    litellm_params:
      model: ollama/qwen2.5:7b
      api_base: http://192.168.1.103:11434
  - model_name: internal-llm
    litellm_params:
      model: ollama/qwen2.5:7b
      api_base: http://192.168.1.104:11434
  - model_name: internal-llm
    litellm_params:
      model: ollama/qwen2.5:7b
      api_base: http://192.168.1.105:11434

router_settings:
  routing_strategy: least-busy # Sends request to the Mac with the fewest current requests
  failover_target: external-gemini # Optional: Fallback model if all local workers are down

2. docker-compose.yml

This script launches LiteLLM and Open WebUI in containers, making them available to your local office network.

version: '3.8'

services:
  # LiteLLM Proxy / Load Balancer
  litellm:
    image: ghcr.io/berriai/litellm:main-latest
    container_name: litellm-gateway
    ports:
      - "4000:4000"
    volumes:
      - ./config.yaml:/app/config.yaml
    command: [ "--config", "/app/config.yaml", "--port", "4000" ]
    restart: always

  # Open WebUI (The User Interface)
  open-webui:
    image: ghcr.io/open-webui/open-webui:main
    container_name: open-webui
    ports:
      - "8080:8080"
    volumes:
      - open-webui:/app/backend/data
    environment:
      - OPENAI_API_BASE_URL=http://litellm:4000/v1
      - OPENAI_API_KEY=anything
      - DEFAULT_MODELS=internal-llm
    depends_on:
      - litellm
    restart: always

volumes:
  open-webui:

Once configurations are set, run:

docker-compose up -d

Your users can now open http://<controller-mac-ip>:8080 in their browsers, sign up, and start chatting!

5. Summary of Benefits & Best Practices

  1. Zero Token Costs: All compute happens locally on the Mac Minis. You only pay for electricity.
  2. Data Security & Privacy: Corporate data and documents processed via Open WebUI (including RAG) never leave your local area network (LAN).
  3. Smart Fallbacks: You can configure LiteLLM to route highly complex tasks (e.g., long-document analysis) to Gemini or OpenAI, while directing 90% of basic daily queries to your local Macs, reducing your API bills drastically.
  4. Active Resource Management: With LiteLLM, you can assign daily token budgets or rate limits to individual users/departments so that no single user monopolizes the local cluster.
